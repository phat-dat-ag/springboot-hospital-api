# P00 Hospital identity and outpatient workflow decisions

## 1. Executive recommendation

**PROPOSED.** Retain the five existing roles and one role per User account. Run the synthetic outpatient demo in a single clinic with STAFF for reception, assigned DOCTOR for care, and ADMIN for administration. Scope clinical access through the encounter assignment, clinician identity link, lifecycle state and purpose. Keep PATIENT self-service and clinical audit review out of the first demo. Approve the STAFF patient flow and the ADMIN cutover before P01. P01 needs no migration. [Readiness roadmap and first implementation phase](HOSPITAL_OUTPATIENT_DEMO_READINESS.md#p-prioritized-implementation-roadmap)

**VERIFIED** describes repository evidence. **INFERRED** describes a conclusion from that evidence. **PROPOSED** means pending approval. **UNKNOWN** identifies a decision or runtime fact that still needs confirmation. This review used source, SQL, contracts and test assertions. Runtime and test execution were outside this assessment.

## 2. Existing five-role implementation

**VERIFIED.** User persists a single numeric role, defaults new accounts to USER, and issues a scalar role claim with the User UUID as JWT subject. The schema's lower-bound check permits values above the five supported codes. Both converters map recognized numbers or equivalent strings to one authority. Missing or unknown role values yield no role authority. Hospital validates incoming User JWTs separately from its outbound service authentication. Role matchers explicitly grant access and the application config defines no role hierarchy. User owns role assignment. A general role-assignment API was not identified in the reviewed User controllers, so elevated demo account provisioning needs an approved existing operational path. ## 4. Role-to-action permission matrix

**PROPOSED.** These are target rules for the staged demo. Unlisted roles receive no permission. Deferred actions have no demo route. Each enabled action uses the same status rules below.

- **401** Missing or invalid bearer authentication, including expiry. Use the route's existing unusable-actor handling in P01 and verify it explicitly. A subsequent confirmed account disablement is an eligibility denial even when the bearer remains cryptographically valid.
- **403** Authenticated caller lacks the action role, required account activation, or a usable clinician identity. Apply action-level checks before resource disclosure.
- **404** Authorized action targeting a missing, inactive or outside-scope record returns an indistinguishable response. Lists omit hidden rows before counting and paging. PAT-002 returns an empty page for zero matches. The table identifies where no singular target exists.
- **409** A visible, otherwise authorized operation conflicts with current state or a business invariant. Check scope before reporting conflicts. Malformed inputs use 400. Required audit failure yields a safe server error with no protected data or partial mutation. An unavailable required identity dependency fails closed with a service error.
- **Eligibility shorthand.** All actors need a trusted UUID subject, permitted role and active account under the freshness policy in §5. **Reception** means STAFF in the approved single-clinic deployment boundary, acting for patient intake. **Assigned** means the caller's DOCTOR subject matches the linked, non-deleted eligible clinician on the encounter. Target doctor checks in the table concern the person being selected or assigned.
- **Audit shorthand.** **Read** means durable access metadata before disclosure, scoped to the resource or returned records, with actor, purpose, outcome, time, and correlation. **Write** means atomic business write and audit, with state or assignment provenance where relevant. **Security** means restricted denial or administration metadata, including when no valid patient FK exists. Exclude tokens, free-text queries, note bodies, findings and contact values from ordinary logs and traces. Existing read/write audit tables are starting points. Search currently records successful access per returned patient, with no per-patient event when empty. [PAT-002](API2-PATIENT-SEARCH.md), [PAT-003](API4-PATIENT-DEMOGRAPHICS.md), [V8](../../db/migration/hospital/V8__attachments_and_audit.sql)

## 5. Resource-level authorization rules

**PROPOSED.** Use explicit method/path role gates and transactional service checks. For shared status PATCH, check the role allowed to request the target action, load the encounter within scope, then evaluate expected status and preconditions. Match the clinician through doctors.external_user_id to the authenticated subject and through encounters.doctor_id to the local doctor. Use active patients, non-deleted clinicians, clinic-zone license date and verified active account linkage. Apply the encounter → patient → doctor lock order for existing visits, patient → doctor for creation, and hold the encounter lock across child writes, signing and completion. Recheck assignment under lock so a racing reassignment cannot leave the former doctor authorized. Filter both projections and counts before pagination. STAFF scope derives from the deployment boundary only in the approved synthetic single-clinic environment. **UNKNOWN** Production site membership, care-team access and emergency access authority. ## 6. Patient and doctor identity linking

**PROPOSED.** User provisions and activates accounts through its approved workflow. Hospital owns chart/profile creation and link, unlink and correction. Ordinary patient registration creates the chart and optional contacts with a null account link. An unlinked patient can receive care. An unlinked doctor profile can exist, but cannot be offered for the interactive demo or act clinically. A disabled or missing linked account blocks portal/clinician use and new assignment where applicable. Preserve chart, clinician authorship and audit, and route existing visits to a supervised reassignment process.

- **Patient.** Require a verified chart identity and proof of control of an activated PATIENT account. Use a short-lived, single-use verified linking ceremony or supervised confirmation tied to the exact chart and token subject. Use an approved registrar attestation and independently authorized Hospital linking operation where required. Email, name, date of birth, MRN and caller-submitted UUID alone are insufficient. Defer minors, delegates and proxy access pending explicit policy.
- **Doctor.** Hospital profile creation is an administrative credentialing workflow. An authorized administrator verifies professional identity, license, clinic eligibility and the intended active DOCTOR account, using approved User provisioning evidence or proof from the doctor's fresh session. Keeping separate profile and account IDs preserves professional attribution after account disablement. Define the no-expiry rule explicitly. Proposed demo default is to seed doctors with known valid expiry.
- **Both.** Lock the target while binding. Check existing ownership and role evidence, enforce the per-table unique external UUID constraints, reject conflicting reuse with a safe 409, and audit custody of link changes in a restricted record. Never replace links silently. Require independent verified correction and an explicit audit trail. The two tables enforce uniqueness independently. **UNKNOWN** Whether production must prohibit cross-table links or allow one person to hold both a chart and a professional profile. With one role, avoid dual usable links for the demo and coordinate any future cross-table invariant transactionally. Patient self-service requires its own ownership and visibility policy before exposure.

**VERIFIED.** V2/V3 provide nullable unique links, and the current doctor mapping and registration endpoint do not provide a link-management workflow. V8 clinical audit is patient-oriented in part, so doctor-only events need a suitable protected administrative sink rather than an invented patient association. ## 8. Single-role versus multi-role assessment

| Model | Simplicity and security | Contract, service and database impact | Demo and future fit |
| --- | --- | --- | --- |
| **A. Single role per user** | Lowest provisioning and review burden. Combine role with existing local relationship and state checks | No User, JWT, other-service or base Hospital schema change | Sufficient for dedicated receptionist, clinician and administrator. Site and team expansion would need stronger scope |
| **B. Multiple roles per account** | Entitlement union can expand access unexpectedly. Requires explicit active duty, provisioning, revocation and audit semantics | A real multi-role model likely needs User persistence changes, migration and a versioned claim/authority rollout across consumers. Violates current constraints if introduced now | Supports dual-duty accounts after demonstrated demand. Adds cross-service coordination |
| **C. Five roles plus scoped grants** | More precise site, delegated intake, reviewer or time-bounded access. Requires approvals, expiry, revocation and review | Hospital-local grants could retain JWT and User schema, but persisted grants need Hospital migration and administration. Shared grants would require explicit integration contracts | Useful for approved production delegation. Existing assignment and link suffice now |

**PROPOSED.** Choose A. A clinician who also performs administration needs both authorities only when that duty is actually required. Use separate, individually attributed clinical and privileged administrative accounts if approved and supported operationally. Keep the clinician profile linked to the DOCTOR account. If one-account dual duty becomes a requirement, prefer narrowly scoped grants for specific Hospital duties and reassess B if the requirement spans services. Avoid shared accounts and blanket clinical access. ## 10. Outpatient workflow refinements

**PROPOSED demo baseline.** Identify or register the chart → create a new encounter → receive the patient → assigned clinician starts examination → record clinical documentation → enter diagnosis disposition → sign assessment → complete → retrieve authorized history. Keep vitals available during examination. A signed assessment and documented diagnosis disposition are required for demo completion, with the demo exercising an approved primary diagnosis. Completion verifies durable prerequisites in the same encounter transaction. [Readiness report](HOSPITAL_OUTPATIENT_DEMO_READINESS.md), [transition policy](../src/main/java/com/hospitalmanagement/hospital/encounter/service/EncounterTransitions.java), [V4](../../db/migration/hospital/V4__medical_encounters.sql), [V5](../../db/migration/hospital/V5__diagnoses.sql)

| Exception | Demo policy and approval boundary |
| --- | --- |
| Unconfirmed diagnosis | Record clinical uncertainty in the draft/assessment. Leave open when the demo's completion policy cannot be satisfied. Clinical owner must approve symptom-based primary coding or a separate documented disposition. V5 lifecycle status does not express certainty. Never fabricate a confirmed code to close |
| Patient cancellation | STAFF records patient-requested cancellation and reason before examination. Patient-facing cancellation and post-start discontinuation require explicit approval |
| Doctor reassignment | STAFF may reassign before start after verifying the replacement and recording old/new assignment and reason. Lock against start. Post-start handoff requires clinical approval, explicit takeover and preserved authorship |
| Interrupted examination | Keep IN_PROGRESS for the same eligible doctor to resume. Preserve drafts and measurements. Approve timeout, escalation and formal suspension/abort rules separately |
| Transfer or referral | Document disposition and referral in the clinical assessment and approved follow-up as appropriate. Formal transfer, clinician takeover and external information exchange require separate policy and workflow |
| Incomplete documentation | Block completion with safe 409. Keep the draft accessible to its authorized author. Use approved addenda/revision paths after signature or completion. Agree on exceptions and follow-up responsibility |
| Repeat visits | Reuse chart/MRN, issue a fresh encounter UUID and visit number. Replays must not create additional visits if durable idempotency is approved. Avoid a blanket same-day uniqueness rule. Apply history scope separately |
