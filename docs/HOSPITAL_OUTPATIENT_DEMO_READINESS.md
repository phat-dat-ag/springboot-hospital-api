# Hospital outpatient demo readiness

## A. Executive summary

**VERIFIED** means checked in the current source, tests, SQL or configuration. **INFERRED** identifies a consequence of that evidence. **PROPOSED** identifies a decision or future implementation. **UNKNOWN** identifies missing runtime evidence or an unsettled business rule. P0 gates the demo, P1 improves the demo or its operational safety, and P2 can follow.

**INFERRED · P0.** V1–V9 provide the clinical data model for a single-clinic outpatient demo. They cover repeat visits, doctor assignment, reception states, observations, notes, diagnoses, follow-up and history. The main gap is the API and authorization layer. Four clinical operations exist. Their current role split prevents one receptionist account from searching, registering and then confirming the same chart. The status route operates on a visit that already exists and can complete it without clinical documentation.

**PROPOSED · P0.** Demonstrate one receptionist, two assigned clinicians, repeat walk-in visits, intake measurements, an assessment with conclusion and advice, a coded diagnosis, controlled completion and a paginated history. Use synthetic data and separate role accounts. Defer PAT-004, contact editing, appointment calendars, patient self-service, billing, inpatient care, pharmacy and laboratory workflows.

**UNKNOWN.** This review derived the resulting schema from all nine SQL migrations. Compose rendered successfully, but Docker daemon access was denied. Applied migration history, live catalogs, key mounts, service health and end-to-end behavior remain unverified. No application tests or database fixtures were run.

## C. Current database suitability

**VERIFIED.** PostgreSQL 17.6 is configured for `clinical_db` and Flyway uses `public`. V1–V9 define 28 business tables plus Flyway's history table. Every business table has a UUID PK with a database default. Clinical FKs use non-cascading behavior. V1/V9 preserve `created_at` on updates and generate `updated_at` with `clock_timestamp()`. Insert defaults generally use `now()`. Histories use `occurred_at`. V9 enforces finite dates, timestamps and relevant numerics and protects all business tables against DELETE and TRUNCATE. The nine soft-delete tables are patients, contacts, doctors, specialties, lab test categories/tests, medication categories/medications and attachments. Soft deletion does not cascade. ## G. Proposed end-to-end outpatient workflow

1. **A · Identify or register.** Search MRN first, otherwise name plus DOB when known. Confirm the candidate using PAT-003 before creating a visit. Show possible matches before registration, allow a deliberate new-chart decision, and never auto-merge or auto-select. Retain today's required MRN/given name and optional family name, DOB, sex and contacts for the demo. Issue MRNs from an approved synthetic series, trim them and handle exact uniqueness conflicts by reopening search. An inactive chart does not appear in normal search and retains its MRN. Route suspected inactive matches or corrections to authorized review. Defer PAT-004. [Registration](API1-PATIENT-REGISTRATION.md), [search](API2-PATIENT-SEARCH.md), [V2](../../db/migration/hospital/V2__patient_management.sql)
2. **B · Register a visit.** Choose the existing patient and an eligible doctor, enter a short visit reason and optional schedule, and submit with a replay key. No appointment is required. A walk-in receives a server-selected clinic-day schedule instant and starts scheduled. Generate a unique opaque encounter number server-side and return the persisted UUID. Lock/recheck patient and doctor eligibility within creation, add initial history from null plus write audit, and warn about another open same-day visit with an approved override. Distinguish replay of one command from a deliberate second visit; avoid blanket uniqueness per patient/day. [V3](../../db/migration/hospital/V3__doctor_management.sql), [V4](../../db/migration/hospital/V4__medical_encounters.sql)
3. **C · Reception and examination.** STAFF receives or cancels permitted visits and may set the initial intake reason. Reassignment before consultation is restricted to the same scope and recorded. DOCTOR may start only their assigned arrived visit. Reuse existing transition, clock and locking rules. Basic eligibility means linked, active doctor with a valid license under clinic-date policy; define how a missing expiry is treated. Optional vitals can be taken after arrival by approved intake staff or the assigned doctor. Staff can record the chief complaint; clinician records detailed symptoms in an assessment. Availability calendar and live capacity are deferred. [ENC-001](API3-ENCOUNTER-STATUS.md), [V4](../../db/migration/hospital/V4__medical_encounters.sql)
4. **D · Document.** Collect observations in a draft assessment with sections for symptoms, findings, conclusion, advice and follow-up. Store the assessment in existing note content and actual numeric observations in separate vital sets, with units and recorder. Accept an active diagnosis catalog code and optional clinical text. The assigned doctor edits their draft, reviews the current snapshot and signs explicitly. Persist author and signature instant server-side. For the first demo, follow-up advice in the note is sufficient; structured follow-up tracking can use `follow_up_plans` later. [V4](../../db/migration/hospital/V4__medical_encounters.sql), [V5](../../db/migration/hospital/V5__diagnoses.sql)
5. **E · Complete.** Proposed minimum policy requires the assigned doctor, in-progress state, one signed assessment with a conclusion, and one active primary diagnosis. Vitals and follow-up are optional. If clinical leadership needs a documented undifferentiated outcome, approve its representation before enabling it. Reception cannot complete. Incomplete visits remain in progress and recoverable on refresh. Keep signed and completed content protected; permit reasoned addenda and diagnosis revisions only once correction authorization and history are implemented. Defer reopening and post-start abort policy. [Transitions](../src/main/java/com/hospitalmanagement/hospital/encounter/service/EncounterTransitions.java), [V9](../../db/migration/hospital/V9__integrity_guards_and_query_indexes.sql)
6. **F · Retrieve history.** Open an authorized patient summary and reverse-chronological visit list with date/status/doctor and scoped reason. Open one visit for signed assessment, diagnosis, vitals, conclusion and authorized status events. Keep drafts visible to authorized authors in the workspace. Show inactive or corrected material only through approved views. Use a small encounter header and bounded child collection APIs so reads, authorization and pagination stay explicit. The initial doctor history lists assigned visits only unless a separate treatment relationship is approved. [V4](../../db/migration/hospital/V4__medical_encounters.sql), [V8](../../db/migration/hospital/V8__attachments_and_audit.sql)

## I. Proposed API contracts

**PROPOSED · P0 unless stated.** Preserve existing envelopes, UUIDs, lower-case lifecycle codes and ISO dates/instants. Use server-authoritative visit and signature times, clinic-local day converted to an inclusive/exclusive UTC range, and allowlisted fields. New creates return 201 with a resource identifier and location, changes and reads return 200. Use bounded pages or opaque cursors with deterministic time plus UUID ordering. Scope before slicing or counting. Required access audit commits before disclosure. Keep details and list responses `no-store`. Use 400 for malformed input; 401 for missing/invalid authentication; 403 for role or action denial; scope-safe 404 for unknown/out-of-scope resources; 409 for lifecycle, prerequisites or changed replay payload. Use 428/412 only where a new conditional update explicitly defines an `If-Match` contract.

| --- | --- |
| GET `/doctors` | Bounded name filter/page → eligible doctor UUID, display name and optional specialty. Avoid external user IDs and license numbers. Eligibility checked again on write. |

P1 if audit policy requires new durable assignment history. |
